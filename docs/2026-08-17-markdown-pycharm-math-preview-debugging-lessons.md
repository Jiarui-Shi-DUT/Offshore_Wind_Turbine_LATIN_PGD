# 1. 本次问题的背景

在整理以下 LATIN-PGD 理论阶段总结时：

`2026-08-17-tower-latin-pgd-eq73-77-global-finishing-stage-summary.md`

文档正文接近 4000 行，包含大量数学公式。Markdown 源码本身可以正常打开，但 PyCharm 的 Markdown Preview 在部分位置开始出现异常：

- 标题和普通文字仍能正常渲染；
- 数学公式从某一处开始显示为原始 LaTeX 源码；
- 一旦某个公式触发异常，其后的多个公式也可能连续失效；
- 同一份文档的不同拆分版本表现不同；
- 最终完整修复版从头到尾可以正常 Preview。

这次排错的最大价值并不只是修复一个 Markdown 文件，而是建立了一套以后编写长篇科研推导文档时可以重复使用的诊断方法。

---

# 2. 最终确认的直接触发因素

本次问题最终通过最小化测试确认：

> **数学环境中直接书写原始字符 `<`，会触发当前 PyCharm Markdown Preview 的数学渲染异常。**

例如，以下写法存在风险：

```markdown
$$ 0\le D_i<D_{\max} $$

$$ 0<\mu\le 1 $$
```

而改成 LaTeX 命令后可以正常显示：

```markdown
$$ 0\le D_i\lt D_{\max} $$

$$ 0\lt\mu\le 1 $$
```

进一步的最小测试文件中完全不包含原始 `<` 字符，仅使用 `\lt`，PyCharm Preview 可以全部正常渲染。

因此，本项目后续 Markdown 文档应采用如下固定规则：

$$ a\lt b $$

而不要在数学环境中直接写原始小于号。

---

# 3. 对“根因”的准确表述

本次可以**经验性确认**的是：

> 在当前 PyCharm Markdown Preview 环境中，数学公式内的原始 `<` 字符会导致数学渲染失效。

但不应进一步武断声称：

> PyCharm 内部一定是因为某个具体 HTML parser bug 才失败。

更准确的表述是：

- Markdown 本身允许 `<` 出现在普通文本中；
- 但在当前 PyCharm Preview 的实际渲染链路中，原始 `<` 与数学公式组合后产生了稳定可复现的问题；
- 将 `<` 替换为 `\lt` 后问题消失；
- 因此工程上应绕开该字符，而不是依赖 IDE 内部实现细节。

也就是说，我们已经确定了**可操作的触发条件和修复方法**，但没有必要对 PyCharm 内部解析机制做未经证实的推断。

# 4. 本次排错过程中曾出现的错误判断

这次排错过程中有几个值得明确记录的错误方向。

## 4.1 错误方向一：怀疑长文档公式数量过多

最开始看到：

- 文档约 4000 行；
- 数学块数量很多；
- Preview 在后半部分失效；

很容易怀疑：

> PyCharm 对 display math block 数量存在某种上限。

但后续证据并不支持这一判断。

因为：

- 一些较短拆分文档仍然失败；
- 另一些包含大量公式的拆分文档却正常；
- 最终完整文档在只修复 `<` 后可以从头到尾正常显示。

因此：

> **文档长度和公式数量不是本次问题的根因。**

以后不能仅凭“长文档在后半段坏掉”就直接推断为渲染数量上限。

---

## 4.2 错误方向二：怀疑文件名或缓存

曾经观察到某个带 `(1)` 后缀的文件可以显示，而原文件不行，因此一度怀疑：

- 文件路径缓存；
- PyCharm Preview 缓存；
- 文件名导致的异常状态。

这种怀疑在当时有一定合理性，但不能作为结论。

后续通过内容级最小复现证明，真正触发因素仍然位于 Markdown 数学内容本身。

因此经验是：

> **文件名变化造成“暂时正常”只能视为线索，不能视为根因证明。**

在科研代码与文档排错中，必须优先寻找可以最小复现的内容级差异。

---

## 4.3 错误方向三：为了减少公式块数量，把独立公式改成 `$...$`

为了尝试减轻 Preview 负担，曾把许多独立公式从：

```markdown
$$ ... $$
```

压缩为独立一行的：

```markdown
$...$
```

这反而使文档的数学排版语义变得不稳定。

对于科研推导文档：

- 行内公式应真正嵌入句子；
- 独立展示的公式应继续使用 display math；
- 不应为了“减少 block 数量”而牺牲数学结构。

因此后续固定采用：

- prose 中的小变量：`$...$`；
- 独立公式：`$$ ... $$`。

---

## 4.4 错误方向四：修改太多变量，导致难以判断真正原因

排错初期同时改变过：

- 文件名；
- 文档长度；
- 公式块形式；
- Markdown 表格；
- 文档拆分方式。

这会带来一个典型问题：

> 当 Preview 恢复正常时，不知道究竟是哪一项修改起作用。

后面采用二分法和最小测试后，才真正建立了因果关系。

因此以后排错必须坚持：

> **一次只改变一个变量。**

---

# 5. 本次最有效的诊断步骤

真正有效的排错流程如下。

## 5.1 第一步：建立最小数学渲染基线

首先建立只有几个公式的测试文件，例如：

```markdown
Inline formula: $s_i$.

$$ i $$

$$ s_i $$

$$ \hat s_{i+1/2} $$

$$ \mathcal E_{\rm tower}=H(H^TMC_0H)^{-1}H^TMC_0 $$
```

该文件可以正常显示。

这一步确认：

> PyCharm 的 Markdown 数学渲染功能总体可用。

因此问题不是全局 Markdown math support 被关闭。

---

## 5.2 第二步：从原文档截取前缀

从长文档中原样截取第 1–10 节，不修改公式。

该前缀可以正常显示。

这一步确认：

> 文档开头语法没有破坏整个 parser，问题位于后续内容。

---

## 5.3 第三步：二分拆分问题区间

随后逐步将问题文档拆成：

- A / B；
- A1 / A2；
- A2-1 / A2-2；
- A2-2a / A2-2b；
- 58–61 / 62–65；
- 58–59 / 60–61。

这种方法本质上是对 Markdown 内容做 binary search。

其优势是：

- 每一次测试都能把问题区间缩小约一半；
- 不需要依靠肉眼浏览数千行公式；
- 很快可以将问题缩小到几个小节。

这是本次最值得保留的诊断经验之一。

---

# 6. 关键定位：第 60–61 节中的 `<`

当问题最终缩小到第 60–61 节时，Preview 中第一条明显失效的公式具有如下结构：

```markdown
$$ 0\le D_i<D_{\max} $$
```

该公式正好包含原始 `<`。

随后设计专门的比较符号测试，最终确认：

- 只要文件中首先出现这种危险写法，后续数学渲染可能一起失效；
- 完全不用原始 `<`，改用 `\lt` 后，测试全部正常。

这是从“相关性”升级到“最小可复现因果证据”的关键一步。

---

# 7. 为什么一个错误公式会影响后续大量公式

本次 Preview 的表现不是：

> 只有包含 `<` 的那一条公式显示错误。

而是：

> 从该公式开始，后面相当一段数学内容都可能进入异常状态。

这意味着 Markdown/Math 渲染错误具有**级联效应**。

因此以后看到：

- 第 60 节开始坏；
- 第 61、62、63 节也坏；

不能认为每一节都有问题。

更合理的第一判断是：

> **第一条坏掉的公式之前或其中，可能存在一个会破坏后续 parser 状态的触发字符。**

所以排错时最重要的不是寻找“所有坏公式”，而是寻找：

> **第一条开始异常的公式。**

# 8. 后续 Markdown 数学公式的强制书写规范

从本次经验出发，本项目 `docs/` 目录建议固定采用以下规范。

## 8.1 小于号

数学环境中禁止直接写原始 `<`。

使用：

```markdown
$\lt$
```

或：

```markdown
$$ a\lt b $$
```

例如：

$$ 0\le D_i\lt D_{\max} $$

$$ 0\lt\mu\le1 $$

---

## 8.2 大于号

虽然本次没有证明原始 `>` 一定会触发同样的问题，但为了语法对称和可移植性，建议在正式数学公式中也优先使用：

```markdown
\gt
```

或已有的：

```markdown
\ge
```

例如：

$$ a\gt0 $$

$$ x\ge0 $$

而不是依赖原始 `>`。

---

## 8.3 小于等于与大于等于

继续使用标准 LaTeX：

```markdown
\le
\ge
```

例如：

$$ 0\le D\le D_{\max} $$

---

## 8.4 独立公式

独立公式统一使用：

```markdown
$$ ... $$
```

并尽量保持一个 display formula 在同一物理行内。

例如：

```markdown
$$ \mathcal E_{\rm tower}=H(H^TMC_0H)^{-1}H^TMC_0 $$
```

不再为了“减少 block 数量”改成单 `$...$`。

---

## 8.5 行内公式

真正嵌入句子的变量和短关系使用：

```markdown
$...$
```

例如：

> 当前 LATIN iteration 记为 $i$，上一 accepted state 为 $s_i$。

---

## 8.6 不使用 `\[`、`\]`、`\(`、`\)`

本项目统一使用：

- inline：`$...$`
- display：`$$...$$`

这样可以减少不同 Markdown renderer 之间的差异。

---

## 8.7 避免不必要的复杂 LaTeX 文本命令

继续遵循之前形成的规范：

- 不滥用 `\boldsymbol`；
- 不在公式里塞入过长 `\text{...}`；
- 长解释写到公式外的 Markdown prose 中；
- 公式只保留真正的数学结构。

这有利于：

- PyCharm Preview；
- Git diff；
- GitHub Markdown；
- 后续人工复核。

---

# 9. Markdown 表格中的数学公式要谨慎

本次最终问题不是表格造成的，但排错过程中曾为了降低潜在干扰而移除表格。

以后建议：

> 对包含长公式、复杂 LaTeX 或多行解释的内容，不优先使用 Markdown table。

原因不是“表格一定有 bug”，而是：

- 表格本身就是额外的 Markdown parser context；
- 复杂公式嵌套其中时调试困难；
- Git diff 可读性差；
- 长文本在 PyCharm Preview 中也不够稳定。

科研推导总结更适合：

- 小节；
- bullet list；
- numbered list；
- 独立 display formulas。

---

# 10. 长文档本身不是问题，但应保持模块化

本次最终完整文档约 3942 行、500 个 display math blocks，在修复 `<` 后可以正常 Preview。

因此不能得出：

> 长 Markdown 文档不能用于 PyCharm。

正确结论是：

> 长文档可以正常工作，但越长，单个隐藏语法触发点越难定位。

因此后续即使保留长文档，也建议在逻辑上模块化：

1. theory source；
2. derivation；
3. numerical interpretation；
4. tower mapping；
5. implementation contract；
6. consistency tests。

这样即使以后再次出现 Preview 问题，也容易通过 section boundary 做二分排查。

# 11. 建议增加 Markdown 数学静态检查

后续生成正式阶段总结后，可以在保存前做一次自动扫描。

最低要求是：

> 检查数学环境中是否出现原始 `<`。

理想的检查逻辑应：

1. 跳过 fenced code blocks；
2. 区分 inline math 与 display math；
3. 只检查数学环境内部；

# 12. 未来文档生成后的固定检查顺序

以后每次生成新的 LATIN-PGD 阶段总结，建议固定执行以下流程。

## Step 1：源文件规范检查

确认：

- inline math 使用 `$...$`；
- display math 使用 `$$...$$`；
- 数学环境中没有原始 `<`；
- 不使用 `\[` / `\]` / `\(` / `\)`；
- 没有未闭合的 `$` 或 `$$`；
- fenced code block 已闭合。

---

## Step 2：PyCharm Preview 人工检查

重点不是逐字看全文，而是抽查：

- 文档开头；
- 第一个复杂公式段；
- 文档中部；
- 文档后半部；
- 最后一节。

如果这几个区域都正常，再进行整体快速滚动检查。

---

## Step 3：如果出现 Preview 异常，先找“第一条坏公式”

不要从整篇文档开始大规模重写。

应先回答：

> 哪一条公式是第一个没有正常渲染的公式？

然后检查其附近：

- `<`；
- `>`；
- `$` / `$$` 闭合；
- code fence；
- HTML-like token；
- Markdown table boundary；
- 反斜杠转义。

---

## Step 4：最小复现

把第一条异常公式复制到一个 10–20 行的独立 Markdown 文件中。

如果最小文件也失败：

> 问题在公式本身。

如果最小文件正常：

> 问题可能来自其前面的 parser state。

---

## Step 5：二分定位

如果无法直接找到触发点：

- 截取前半篇；
- 测试；
- 再对异常半区继续二分。

这种方法比人工逐行扫描数千行 Markdown 高效得多。

---

## Step 6：一次只改一个因素

排错时不要同时：

- 改文件名；
- 改公式；
- 改表格；
- 拆文件；
- 改 `$` / `$$`；
- 改标题结构。

否则即使修好，也无法知道真正原因。

# 13. 对 Git 工作流的经验

这次还形成了一个很重要的 Git 文档管理经验。

在 Preview 尚未确认正常之前：

> 不要 `git add`，更不要 `git commit`。

所有：

- split；
- diagnostic；
- test；
- fixed；
- temporary copy；

都只应视为本地临时文件。

最终只有经过：

1. 内容确认；
2. PyCharm Preview 确认；
3. 文件名确认；

之后，才进入 Git 正式保存流程。

# 14. 临时文档必须在提交前清理

- `part-a`
- `part-a1`
- `part-a2`
- `a2-1`
- `a2-2`
- `diagnostic`
- `test`

文件。

最终通过：

```powershell

```

# 17. 对科研软件开发过程的更一般经验

这次 Markdown 问题虽然不是求解器算法问题，但它体现了与数值算法调试完全相同的原则。

## 17.1 不要凭现象直接猜根因

“后半段坏了”不等于“文档太长”。

“改文件名后好了”不等于“缓存是根因”。

必须建立可复现证据。

---

## 17.2 优先最小可复现案例

无论是：

- Markdown Preview；
- LATIN residual；
- PGD fixed-point；
- tower equilibrium；
- material integration；

如果问题复杂，最有效的方法通常都是把系统缩小到最小案例。

---

## 17.3 二分定位比无目标修改更可靠

本次从数千行文档逐步缩小到：

- A2；
- A2-2；
- A2-2a；
- 58–61；
- 60–61；

本质上和数值软件中定位：

- 哪个 iteration；
- 哪个 time step；
- 哪个 element；
- 哪个 Gauss point；
- 哪个 fiber；

完全是同一种调试思想。

---

## 17.4 修复后必须做全量回归检查

找到 `<` 后，不应该只修第 60 节。

最终做法是：

> 扫描完整文档中数学环境里的所有原始 `<`。

本次最终共替换 8 处，并确认：

> remaining raw `<` inside math = 0。

随后再对完整文档从头到尾 Preview。

这和代码修复后的 regression test 是同一个原则。

# 18. 后续固定的 Markdown 安全规则

以后本项目所有长篇理论 Markdown 文档，建议默认遵守以下规则：

1. 数学环境内不用原始 `<`，统一写 `\lt`。
2. 数学环境内优先不用原始 `>`，统一用 `\gt`、`\ge` 等 LaTeX 命令。
3. inline math 用 `$...$`。
4. display math 用 `$$...$$`。
5. 独立公式不要为了压缩 block 数量改成 `$...$`。
6. 不使用 `\[`、`\]`、`\(`、`\)`。
7. 尽量避免复杂公式放在 Markdown table 中。
8. 一个 display formula 尽量保持一条物理行。
9. 长解释写在公式外。
10. 生成后先 Preview，再进入 Git。
11. Preview 出错时先找第一条坏公式。
12. 无法定位时采用最小复现 + 二分法。
13. 排错阶段一次只改变一个变量。
14. 所有 diagnostic/test/split 文件在提交前清理。
15. 正式文件名不保留 `fixed`、`test`、`(1)` 等调试后缀。

# 19. 建议增加的自动化 lint 条件

未来可以为 `docs/*.md` 增加一个轻量检查器，至少检查：

- 未闭合的 inline `$`；
- 未闭合的 display `$$`；
- 数学环境内原始 `<`；
- 数学环境内原始 `>`；
- 未闭合 fenced code block；
- `\[` / `\]` / `\(` / `\)`；
- 明显不必要的独立 `$...$` 行。

该检查器不需要复杂 Markdown AST，只需做面向本项目约定的 deterministic scanner 即可。

# 20. 本次最重要的结论

本次经验最终可以浓缩为三点。

第一：

> **不要把 PyCharm Preview 的级联失效误认为长文档本身不可渲染。**

第二：

> **对于当前项目，数学公式中直接出现原始 `<` 是一个已经实际复现的危险写法，应统一改用 `\lt`。**

第三：

> **面对长篇科研 Markdown 的异常，最有效的方法不是反复重写整篇文档，而是：最小复现 → 找第一条异常 → 二分定位 → 单变量修改 → 全量回归检查。**

这套流程以后不仅适用于 Markdown 文档，也应继续用于 LATIN-PGD 求解器和 tower fatigue implementation 的数值调试。
